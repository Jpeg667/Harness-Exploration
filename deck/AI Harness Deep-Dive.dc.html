An agent harness is the software layer surrounding an LLM that lets it function as an agent: it manages prompts, context, tool use, memory, execution state, permissions, and the processing of results.

The one-liner

The model supplies the reasoning. The harness supplies the ability to act.

01 · WHAT A HARNESS IS

"Harness" is an overloaded word

Agent harness ← THIS DECK

Runtime scaffolding that turns a model into a working agent: loop, tools, context, memory, permissions. Ships as a product — Claude Code, Codex, Hermes Agent, Odysseus.

Test / eval harness

Infrastructure for measuring a model: runs it against benchmark suites (SWE-bench, evals), scores outputs, compares versions. Exists to judge the model, not to help it act.

Caution

The two overlap in one place: benchmark results depend heavily on which agent harness the model ran inside. "Model X scored 70% on SWE-bench" always means "model X inside some specific harness."

CHECKPOINT · SECTION 01

Recall — answer before you open

Q1 · The missing capability

A bare LLM API call can't edit a file. What makes that possible in an agent, and what does the model itself actually contribute?

The harness defines tools and runs the loop; the model only emits a structured request to use a tool. The harness executes it and feeds the result back. Model = reasoning, harness = action.

Q2 · Two harnesses

Agent harness vs test harness — one sentence each.

Agent harness: runtime scaffolding that lets a model act (loop, tools, context, memory, permissions). Test harness: measurement scaffolding that runs a model against benchmarks and scores it.

Q3 · Statelessness

Why does "the model is stateless" force the harness to exist?

Because nothing persists inside the model between API calls — every scrap of continuity (conversation so far, tool results, memory) must be stored by the harness and re-sent every call.

Why it works

Each pass, the model sees everything that has happened so far and decides the single next action. Intelligence stays in the model; the loop just keeps handing it an updated world-state.

Hold onto this

Every harness — Claude Code, Codex, Hermes, yours — is this same loop with better plumbing. Nothing in §03–§05 replaces it; it all hangs off it.

02 · THE AGENTIC LOOP

How the loop ends

The model decides · stop_reason
  • tool_use — "I need another action" → loop continues
  • end_turn — "I'm done, here's my answer" → loop exits
  • max_tokens — output cut off → retry with more room (next slide)
The harness decides · guardrails
  • max iterations / token budget / wall-clock cap
  • user interrupt (Esc in Claude Code)
  • loop detection — same failing call repeated
Caution

A loop with no harness-side cap is an unbounded spend. The model wants to keep trying; the harness is where "stop after N attempts, report what you learned" lives.

02 · THE AGENTIC LOOP

Every stop_reason, and what the harness does

stop_reasonThe model is sayingHarness action
tool_use"Run these, then I'll continue"execute every tool_use block, append results, loop
end_turn"Done, here is my answer"exit the loop, hand text to the user
max_tokens"I was cut off" — output hit the capretry the same request with a bigger max_tokens; if a tool_use block is present, its input is truncated: never run it
stop_sequence"I emitted one of your stop strings"treat like end_turn; the string itself is in stop_sequence
pause_turn"A server-side tool loop hit its limit"re-send the same transcript unchanged so the server resumes; do not append "Continue"
refusal"Safety classifier declined this turn"never execute that turn's tools; surface to the user or fall back to another model
The trap11

A tool_use input cut off by max_tokens often parses fine: the SDK's tolerant JSON parser returns a valid partial object. No exception fires. The only signal is stop_reason == "max_tokens", so check it before dispatching anything.

Why not "Continue."?11

The old trick was to leave the truncated assistant turn in place and let the model resume it (prefill). Current models reject a trailing assistant message with a 400. The transcript has to end on a user turn, so the fix is to discard the cut-off turn and retry with room.

What the harness must do
text_delta
print immediately: this is the whole reason to stream
input_json_delta
fragments of one JSON string; buffer per block index, parse only at content_block_stop
message_delta
carries stop_reason and final output usage: the branch point of the loop
append
rebuild the full assistant content list from the blocks and append it to the transcript, same as non-streaming
Why it matters10

Nothing about the loop changes. What changes is that the assistant turn is no longer handed to you whole: the harness now owns reassembly, and a bug there (a dropped fragment, parsing before stop) corrupts the transcript for every later iteration.

02 · THE AGENTIC LOOP

Every harness has one loop — find it

Open any harness's source and somewhere there is one loop. In a small harness it is one function; in a big one it is split across a pipeline of phase modules. Either way, everything else — tools, memory, UI — is called from it. Finding where it lives tells you how the whole product works.

Hermes · where the loop lives6

The AIAgent class is in run_agent.py, assembled from mixins. The loop body is agent/conversation_loop.py (about 1,800 lines), which calls a pipeline of agent/turn_* phase modules: request assembly (system prompt + memory + transcript), API call and error handling (retries), response intake, tool round, finalizer. Same five concerns as our 50-line loop, one module each. The subsystems of §03–§05 are exactly the things these phases call out to.

Study move

When evaluating any harness, find its loop file first. Ask: how does it build the prompt, dispatch tools, and decide to stop? Those three answers characterize the product.

CHECKPOINT · SECTION 02

Recall — answer before you open

Q1 · The replay

What exactly gets sent to the model on iteration 7 of the loop?

The system prompt plus the entire message array — all six previous iterations' assistant turns and tool results. The API is stateless; every call replays everything.

Q2 · Whose voice?

Tool results arrive under which role, and why is that a sane design?

Role "user". From the model's perspective there are only two speakers: itself and the world. Tool results are the world answering back.

Q3 · Three exits

Name three distinct ways an agentic loop terminates.

Model returns end_turn (task done); harness cap hits (max iterations / budget / timeout); human interrupts. Bonus: loop detection on repeated identical failures.

Q4 · Cut off mid-call

stop_reason is max_tokens and the turn contains a tool_use block whose input parsed without error. What do you do, and why isn't "it parsed" enough?

Discard the turn and retry with a larger max_tokens. The tolerant parser returns a valid partial object, so a clean parse proves nothing; the stop_reason is the only signal that the input is incomplete. Running it executes a tool with half its arguments.

Q5 · Streaming

In a streamed turn, which event tells the harness which branch of the loop to take, and when is it safe to parse a tool's input?

message_delta carries stop_reason. Tool input arrives as input_json_delta fragments of one JSON string; buffer them by block index and parse only after that block's content_block_stop.

03 · TOOLS & THE ROUND TRIP

Errors are data, not crashes

Do

When a tool fails — file missing, command non-zero, timeout — return the error text as the tool_result. The model reads it and self-corrects on the next iteration ("the file moved; searching for it…"). Agent robustness comes from this, not from harness cleverness.

Don't

Never let a tool exception kill the loop, and never silently swallow a failure. An empty tool_result makes the model hallucinate success — the worst possible outcome.

  • Parallel calls — one assistant turn may carry several tool_use blocks; run them concurrently, return all results in one message.
  • Timeouts — every execution gets a deadline; a hung shell command must become an error string, not a hung agent.
  • Output caps — truncate huge results before appending (§04 explains why).
03 · TOOLS & THE ROUND TRIP

Parallel tool calls, mechanically

assistant turn · two requests at once
{"role": "assistant", "content": [
  {"type": "tool_use", "id": "tu_1",
   "name": "read_file", "input": {"path": "auth.py"}},
  {"type": "tool_use", "id": "tu_2",
   "name": "read_file", "input": {"path": "tests/test_auth.py"}}
]}
user turn · ONE message, every result
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "tu_1",
   "content": "def check_token(t): ..."},
  {"type": "tool_result", "tool_use_id": "tu_2",
   "is_error": true,
   "content": "FileNotFoundError: tests/test_auth.py"}
]}
  • Run them concurrently — a thread pool or async gather; each still gets its own timeout and output cap.
  • Answer every id — one tool_result per tool_use, in one user message. A failed one is is_error: true with the error text, not a missing entry.
  • Opt out per request — tool_choice: {"type": "auto", "disable_parallel_tool_use": true} caps it at one call per turn, for tools with side effects that must be ordered.
Don't split the results11

Returning two results as two user messages leaves a tool_use without its matching result in the same turn. Anthropic's docs warn that this silently trains the model to stop making parallel calls, so the agent gets slower and you won't know why.

   "description":"Read a file…","inputSchema":{…}}]}}

How it plugs into the loop
tools/list → tools[]
each entry's name, description, inputSchema becomes a tool schema exactly like the hand-written one, re-advertised every call
tool_use → tools/call
the dispatch table's entry for an MCP tool is "forward name + input to that server"
result → tool_result
content array flattens to the tool_result content; isError maps to is_error
transports
stdio (spawn a process, JSON per line) or Streamable HTTP (one POST endpoint, optional SSE stream back)
Why it earns the "USB port" line12

The loop never learns a new integration. Any process that speaks these four messages shows up as ordinary tools, and the same server works under Claude Code, Hermes, or your 50 lines.

CHECKPOINT · SECTION 03

Recall — answer before you open

Q1 · Where's the code?

A tool definition contains no code. Where does the code live, and how does a tool_use block find it?

In the harness — a dispatch table keyed by tool name. The tool_use block's "name" field is the lookup key; "input" becomes the arguments.

Q2 · The gap

Why is "the model never executes anything" the foundation of agent safety?

Because every dangerous action passes through the harness between request and execution — that gap is where validation, permission gates, and sandboxes can exist at all.

Q3 · Failed tool

read_file throws FileNotFoundError. What should the harness send back, and what happens next?

A tool_result whose content is the error text. Next iteration the model sees it and adapts — lists the directory, searches, or asks. The loop never crashes.

Q4 · Two at once

The model emits two tool_use blocks in one turn. How many user messages go back, and what must each result carry?

One user message containing both tool_result blocks, each with the matching tool_use_id; a failure is is_error: true with the error text, never a missing entry. Splitting across messages trains the model away from parallel calls.

Q5 · MCP handshake

Name the JSON-RPC messages a harness exchanges with an MCP server before it can run a tool, and what it does with the tools/list result.

initialize (request/response), the notifications/initialized notification, then tools/list. Each listed tool's name, description and inputSchema becomes an entry in the tools[] array advertised to the model; tools/call is the dispatch target.

Q6 · Other provider

Where does OpenAI's Chat Completions put the tool arguments, and what does your dispatch code have to do differently?

In tool_calls[].function.arguments as a JSON string, not an object. Dispatch must json.loads it first; on Anthropic, tool_use.input is already parsed.

04 · CONTEXT MANAGEMENT

The window is the agent's entire world

finite
a context window (say 200K tokens) bounds everything the model can consider at once
replayed
the loop re-sends the whole transcript every iteration — growth compounds in cost and latency
tool-fat
tool results dominate: one file read or test log can outweigh fifty turns of conversation
Why this is a harness job

The model can't manage its own diet — it only ever sees what it's fed. Deciding what enters, what stays, and what gets summarized away is pure harness engineering, and it's what separates a demo from a product.

04 · CONTEXT MANAGEMENT

The four standard moves

  1. Trim tool results — cap every result at N chars on append; drop or shrink old ones once they've been acted on.
  2. Compact — near the limit, have the model summarize the transcript-so-far into one message; keep decisions, drop transcripts.
  3. Isolate with sub-agents — spawn a fresh loop with its own empty window for a side-task; only its final report returns to the parent.
  4. Retrieve instead of stuffing — keep knowledge outside the window (files, DB) and pull only what the current step needs.
Hermes · memory over retrieval1

Hermes stores session history in SQLite with FTS5 full-text search and uses LLM summarization for cross-session recall — move 4 made permanent. Past sessions aren't in the window; they're indexed and retrieved on demand.

CHECKPOINT · SECTION 04

Recall — answer before you open

Q1 · The fat

Why do tool results, not conversation, dominate context consumption?

Turns of dialogue are short; tool results are raw world-output — whole files, test logs, web pages. One read_file can outweigh dozens of exchanges, and the loop replays all of it every iteration.

Q2 · The trade

What does compaction keep and what does it sacrifice?

Keeps decisions, conclusions, and current task state; sacrifices verbatim detail (exact file contents, full logs). The agent can re-fetch details through tools; it can't re-derive lost decisions.

Q3 · Sub-agents

How does spawning a sub-agent help with context, specifically?

The side-task's noisy tool traffic happens in the sub-agent's own fresh window and dies with it — only a short final report enters the parent's transcript.

05 · THE REST OF THE ANATOMY

System prompt: the standing orders

Pinned first in every single API call, invisible to the user, written by the harness. Four jobs:

Identity
who the agent is, its voice and priorities
Rules
hard constraints: never push to main, ask before deleting
Environment
cwd, OS, date, repo layout — injected fresh each session
Tool guidance
when to prefer which tool, output conventions
Hermes · SOUL.md4

Hermes makes identity a user-editable file: SOUL.md holds the agent's persona and priorities per profile, next to its config.yaml. Editing a markdown file re-personalities the agent — the system prompt made into a surface, not a secret.

05 · THE REST OF THE ANATOMY

Memory: surviving the end of the window

Working memory

The transcript itself. Perfect fidelity, zero effort — and gone when the session ends or compaction eats it.

Persistent memory

Written to disk by the harness and re-injected later: instruction files (CLAUDE.md / AGENTS.md), fact databases, session summaries.

Hermes · holographic memory5

An agent-curated fact store (SQLite + FTS5): the harness periodically nudges the model to record what it learned, and retrieval searches those facts across sessions. The agent maintains its own notebook rather than the user maintaining it.

Trade-off

Memory injected every session is a standing tax on the window and can go stale. Curation — deciding what not to remember — is the hard part.

05 · THE REST OF THE ANATOMY

Permissions and sandboxing

Threat model

A shell tool is arbitrary code execution driven by a model that can be wrong or prompt-injected by content it reads. Two defense layers exist:

1 · Permission gates

Before execution: allow-lists (reads auto-approve), deny-lists (rm -rf, git push), and ask-the-human for everything ambiguous. Claude Code's approval prompts live here.

2 · Sandboxes

During execution: contain the blast radius — containers, scoped filesystem mounts, no-network defaults, throwaway VMs. Assume the gate will someday let a bad call through.

In the wild17

Hermes runs its shell through seven pluggable backends — local, Docker, SSH, Singularity, Modal, Daytona, Vercel Sandbox. Odysseus runs agents inside a Docker container whose compose file mounts only specific host directories (data, logs, caches) and deliberately not the Docker socket — though shell commands can still reach anything inside that container: scope carefully.

05 · THE REST OF THE ANATOMY

Skills: procedures as prompts

A skill is a markdown document describing how to do a recurring task — steps, conventions, pitfalls — stored by the harness and injected into context only when relevant. Tools extend what an agent can do; skills extend what it knows how to do, with no new code.

task arrives

Hermes · the self-improving part1

Hermes creates its own skills after finishing complex tasks and edits them as they're used — the "self-improving agent" claim is literally: the harness writes better prompts for its future self. Skills follow the open agentskills.io format, so they port across harnesses.

CHECKPOINT · SECTION 05

Recall — answer before you open

Q1 · Personality

Where does an agent's "personality" physically live, and what does Hermes do differently with it?

In the system prompt the harness pins to every call. Hermes externalizes it as SOUL.md — a user-editable markdown file per profile.

Q2 · Memory vs skills

Both persist across sessions. What's the difference?

Memory stores facts (what is true: preferences, project details). Skills store procedures (how to do things). Facts get retrieved; procedures get followed.

Q3 · Two layers

Why have both permission gates and sandboxes, not just one?

Gates filter intent before execution but will eventually mis-approve (or be injection-tricked); the sandbox bounds the damage when that happens. Defense in depth.

06 · BUILD YOUR OWN

The roadmap: six steps, one afternoon

  1. Pick a provider SDK — any messages-style API with tool support (Anthropic, OpenAI, or OpenRouter for model-agnosticism like Hermes).
  2. Write a minimal system prompt — identity, one paragraph; environment info (cwd, OS); ground rules.
  3. Define 2–3 tools — read_file, run_shell, write_file cover 90% of coding-agent behavior. Schema + python function each.
  4. Write the loop — call, append, check stop_reason, repeat. (Next slide.)
  5. Dispatch + append results — execute by name, wrap errors as strings, cap output size. (Slide after.)
  6. Add stop conditions — max iterations and a ctrl-C handler. Now it's safe to leave running.
The takeaway

A working harness is ~50 lines. Everything that makes Claude Code or Hermes feel magic is iteration on those 50 lines, not a different idea.

06 · BUILD YOUR OWN · SKELETON 1/2

harness.py — the loop

import anthropic
client = anthropic.Anthropic()
 
SYSTEM = "You are a coding agent. Use tools;
          verify your work before finishing."
 
def run_agent(task):
    messages = [{"role": "user", "content": task}]
    budget = 4096
    for _ in range(40):              # stop condition
        resp = client.messages.create(
            model="claude-sonnet-5",
            system=SYSTEM,
            tools=TOOL_SCHEMAS,        # part 2
            messages=messages,
            max_tokens=budget)
        if resp.stop_reason == "max_tokens":   # cut off: never run a
            budget *= 2                          # truncated tool call;
            continue                            # retry with room
        messages.append({"role": "assistant",
                         "content": resp.content})
        if resp.stop_reason != "tool_use":
            return resp                # end_turn → answer
        messages.append(run_tools(resp))  # part 2

TOOLS = {
  "read_file": lambda path: open(path).read(),
  "run_shell": lambda command: subprocess.run(
      command, shell=True, capture_output=True,
      text=True, timeout=60).stdout,
}
 
def run_tools(resp):
    results = []
    for block in resp.content:
        if block.type != "tool_use": continue
        try:
            out = TOOLS[block.name](**block.input)
        except Exception as e:
            out = f"ERROR: {e}"   # errors are data
        results.append({
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": str(out)[:20000]})  # cap fat
    return {"role": "user", "content": results}

06 · BUILD YOUR OWN

Hardening: what to add, in order

  1. Permission gate safety — allow-list reads, confirm writes and shell; or run the whole thing in Docker.
  2. Context compaction scale — token-count the transcript; summarize when past ~70% of the window.
  3. Retries + timeouts robustness — exponential backoff on API errors; deadline on every tool.
  4. Persistent memory quality — start with one markdown file injected into SYSTEM; SQLite later.
  5. Streaming UI feel — print text deltas and tool calls as they happen; silence reads as a hang.
  6. Sub-agents + skills power — a sub-agent is just run_agent() exposed as a tool; skills are markdown files matched to the task.
Caution

Don't build 2–6 before you've watched the bare skeleton fail on real tasks. Each subsystem exists to fix a failure you should see first — otherwise you're cargo-culting Hermes's architecture without its lessons.
